# 04. 한국어 사전학습 (vocab 16,000)

작업일: 2026-11-18

## 목표

- [03번 문서](03_한국어_토크나이저.md)에서 만든 한국어 토크나이저로, 한국어 위키백과를 처음부터(무작위 가중치) 사전학습한다.
- 원본 MiniMind 코드는 고치지 않고, 바깥에 작은 스크립트 하나만 추가해서 해결한다.
- 사용할 토크나이저는 **vocab 16,000**으로 정했다. 같은 문장을 더 적은 토큰으로 표현하기 때문이다(압축률이 더 좋음. 설명문 113자 기준 6,400은 57토큰, 16,000은 45토큰). 6,400에도 다음절 조각이 3천 개 넘게 있지만, 16,000에서는 더 많은 단어가 한 덩어리가 된다 ([03번 문서](03_한국어_토크나이저.md#관찰한-점)).
  - 이것은 학습 전 당시의 판단이다. 이후 6,400으로도 같은 조건으로 학습해 검증 세트 BPC로 비교해 보니, **이 규모에서는 6,400이 더 좋았다** (3.2290 vs 3.2997, [05번 문서](05_vocab_비교.md)).

## 1. 학습 스크립트 만들기: `scripts/train_pretrain_ko.py`

### 왜 새 스크립트가 필요했나

원본 `minimind/trainer/train_pretrain.py`는 두 가지가 고정돼 있다.

| 고정된 것 | 원본 코드 위치 | 문제 |
|---|---|---|
| 토크나이저 경로 | `init_model()` 안에서 `../model` 토크나이저를 불러옴 | 한국어 토크나이저(`tokenizers/ko_16000`)를 쓸 수 없음 |
| vocab 크기 | `MiniMindConfig(hidden_size=..., num_hidden_layers=..., use_moe=...)`로 만들어서 `vocab_size`를 넘기지 않음 → 기본값 6,400 | 토크나이저는 16,000개인데 모델 사전(임베딩)은 6,400칸이라 맞지 않음 |

원본 파일을 직접 고치면 나중에 원본을 업데이트하거나 다른 사람이 따라 할 때 차이를 추적하기 어렵다. 그래서 원본은 그대로 두고 바깥에서 불러 쓰는 방식을 택했다.

### 어떻게 만들었나

핵심은 원본의 학습 루프 함수 `train_epoch()`를 **그대로 재사용**하는 것이다.

원본 `train_epoch()`는 함수 인자가 아니라 **모듈 전역 변수**(`args`, `model`, `optimizer`, `scaler`, `autocast_ctx`, `lm_config`)를 참조한다. 원본은 `if __name__ == "__main__":` 블록에서 이 값들을 만든다. 다른 파일에서 `import`하면 이 블록은 실행되지 않으므로, 새 스크립트가 같은 이름의 값을 직접 만들어 모듈에 채워 넣은 뒤 `train_epoch()`를 호출한다.

```python
import trainer.train_pretrain as base

tokenizer = AutoTokenizer.from_pretrained(tokenizer_dir)       # 1. 한국어 토크나이저
vocab_size = len(tokenizer)                                     #    16,000
lm_config = MiniMindConfig(hidden_size=..., num_hidden_layers=...,
                           vocab_size=vocab_size)               # 2. vocab 크기를 토크나이저에 맞춤
model = MiniMindForCausalLM(lm_config).to(args.device)

base.args = args                 # 원본 train_epoch()가 참조하는 전역값을 채운다
base.lm_config = lm_config
base.model = model
base.optimizer = optim.AdamW(model.parameters(), lr=args.learning_rate)
base.scaler = torch.cuda.amp.GradScaler(enabled=(args.dtype == "float16"))
base.autocast_ctx = autocast_ctx

base.train_epoch(epoch, loader, len(loader), 0, None)
```

(전체 코드는 [scripts/train_pretrain_ko.py](../scripts/train_pretrain_ko.py) 참고)

그 밖에 알아둘 점:

- 경로 인자(`--tokenizer_dir`, `--data_path`, `--out_dir`)는 **minimind_ko 폴더 기준**으로 해석한다.
- 원본 `train_epoch()`는 체크포인트를 현재 폴더 기준 `../checkpoints`에 저장한다. 그래서 스크립트가 학습 직전에 작업 폴더를 `minimind/trainer`로 옮긴다. 결과적으로 체크포인트는 `minimind/checkpoints/`에 생긴다(원본을 직접 실행할 때와 같은 위치).
- 원본에 있는 분산 학습(DDP), 이어서 학습하기(`--from_resume`), wandb, `torch.compile`, MoE 옵션은 넣지 않았다. GPU 한 장으로 처음부터 한 번 학습하는 용도만 남겼다.
  - 이후 [06번 문서](06_데이터양_비교.md#실험-조건)의 실험을 위해 `--ckpt_dir`(실행마다 체크포인트 폴더를 따로 지정. 주지 않으면 지금도 위와 같이 `minimind/checkpoints/`에 저장)를, 그 실험 도중에 `--resume 1`(그 폴더의 체크포인트에서 이어서 학습, 원본 `--from_resume`과 같은 방식)을 추가했다. 이 문서의 학습은 두 옵션 없이 돌렸다.

## 2. 데이터 분할: 학습 10만 / 검증 2천

전체 `data/kowiki.jsonl`(118만 5,371 조각)을 다 쓰면 노트북에서 시간이 너무 오래 걸린다. 그래서 일부만 뽑아 학습용과 검증용(held-out)을 따로 만들었다.

```bat
cd /d D:\minimind_ko
.venv\Scripts\python.exe scripts\make_subset.py data/kowiki.jsonl data/kowiki_train_100k.jsonl 100000 11 0
.venv\Scripts\python.exe scripts\make_subset.py data/kowiki.jsonl data/kowiki_heldout_2k.jsonl 2000 11 5
```

| 파일 | 줄 수 | 뽑는 방법 |
|---|---|---|
| `data/kowiki_train_100k.jsonl` | 100,000 | 11줄마다 1줄, 0번째부터 (0, 11, 22, …번째 줄) |
| `data/kowiki_heldout_2k.jsonl` | 2,000 | 11줄마다 1줄, 5번째부터 (5, 16, 27, …번째 줄) |

- 11로 나눈 나머지가 서로 다르기 때문에(0과 5) **두 파일에 같은 줄이 들어갈 수 없다.** 실제로 확인해도 겹치는 줄은 0개였다.
- 검증 세트는 학습에 쓰지 않은 글로 모델을 평가하기 위한 것이다. 학습한 글로 평가하면 "외운 것"과 "배운 것"을 구분할 수 없다.

알아둘 한계 (공부용이라 그대로 진행):
- 검증 세트는 전체 파일의 앞부분(5~21,994번째 줄)에서만 뽑힌다. 2,000줄을 채우면 멈추기 때문이다. 학습 세트는 0~1,099,989번째 줄에 걸쳐 있다.
- 위키 문서 하나가 여러 조각으로 나뉘어 있어서, 같은 문서의 다른 조각이 학습 세트와 검증 세트에 나뉘어 들어갈 수 있다. "같은 문장"은 겹치지 않지만 "같은 주제"는 겹칠 수 있다.
- 토크나이저 학습용 샘플(`data/tokenizer_sample.jsonl`, 0~999,995번째 줄에서 5줄마다 1줄)에 검증 세트 2,000줄 중 400줄(20%)이 들어 있다. 토크나이저가 검증 세트 글을 일부 미리 본 셈이다.

## 3. max_seq_len을 512로 정한 이유

`max_seq_len`은 모델이 한 번에 보는 최대 토큰 수다. 이보다 긴 조각은 뒤가 잘리고, 짧은 조각은 빈칸(padding)으로 채운다. 원본 기본값은 340이다(중국어 기준).

검증 세트 2,000 조각을 두 토크나이저로 잘라서 길이를 재 봤다. 아래 숫자는 학습 때와 같이 앞뒤 특수 토큰(BOS, EOS) 2개를 포함한 길이다.

| 토크나이저 | 평균 | p95 | 최대 | 420 초과 | 512 초과 |
|---|---|---|---|---|---|
| ko_6400 | 363 | 501 | 743 | 34.2% | 4.2% |
| ko_16000 | 316 | 445 | 715 | 8.8% | 0.8% |

(p95: 길이 순으로 줄 세웠을 때 95% 지점의 값. "95%의 조각은 이 길이 이하"라는 뜻)

- 처음에는 420 정도를 생각했지만, 420이면 6,400 쪽은 조각의 34%가 잘린다. 16,000 쪽은 9%만 잘린다.
- 이렇게 되면 나중에 두 토크나이저를 비교할 때 "토크나이저 차이" 대신 "잘린 글의 양 차이"가 섞인다.
- 512로 올리면 둘 다 대부분 안 잘린다(4.2%, 0.8%). 그래서 **두 학습 모두 512**로 통일했다.
- 512가 VRAM 8GB에 들어가는지는 실제 학습으로 확인했다(아래 [6. 결과](#6-결과)의 VRAM 약 6.8GB).

## 4. 학습 설정

| 설정 | 값 | 원본 기본값 | 설명 |
|---|---|---|---|
| tokenizer_dir | tokenizers/ko_16000 | ../model (고정) | 한국어 토크나이저 |
| vocab_size | 16,000 (토크나이저에서 자동) | 6,400 (고정) | |
| data_path | data/kowiki_train_100k.jsonl | ../dataset/pretrain_t2t_mini.jsonl | 한국어 위키 10만 조각 |
| hidden_size / num_hidden_layers | 768 / 8 | 768 / 8 | 모델 구조는 원본과 같음 |
| 파라미터 수 | 71.28M | 63.91M | vocab 증가분만큼 늘어남 ([03번 문서](03_한국어_토크나이저.md#vocab-크기와-모델-크기)) |
| epochs | 1 | 2 | |
| batch_size | 16 | 32 | VRAM 8GB에 맞춤 |
| accumulation_steps | 8 | 8 | 16 × 8 = 128개 조각마다 가중치 1번 갱신 |
| learning_rate | 5e-4 | 5e-4 | 코사인 스케줄로 5e-4 → 5e-5까지 줄어듦 (원본 `get_lr()`) |
| max_seq_len | 512 | 340 | 위 3번 참고 |
| grad_clip | 1.0 | 1.0 | |
| dtype | bfloat16 | bfloat16 | |
| num_workers | 4 | 8 | 노트북 환경 |
| log_interval / save_interval | 50 / 1000 | 100 / 1000 | |
| seed | 42 | 42 | |

step 수 계산: 100,000 조각 ÷ batch 16 = **6,250 step**. 로그의 step은 배치 1번 단위이고, 실제 가중치 갱신(optimizer step)은 8 step마다 1번이라 782번이다 (6,250 ÷ 8 = 781.25, 마지막 step에서 한 번 더 갱신).

## 5. 실행

```bat
cd /d D:\minimind_ko
.venv\Scripts\python.exe -X utf8 scripts\train_pretrain_ko.py --tokenizer_dir tokenizers/ko_16000 --data_path data/kowiki_train_100k.jsonl
```

위 설정 표의 값은 모두 스크립트 기본값이라 두 인자만 주면 된다.

실제 학습은 Git Bash에서 아래 명령으로 실행하고 로그를 파일로 남겼다. 다시 실행해 볼 때는 `tee` 뒤의 로그 파일명을 바꿔야 저장소에 있는 기록(`logs/02_…log`)을 덮어쓰지 않는다.

```bash
set -o pipefail; cd /d/minimind_ko && PYTHONUNBUFFERED=1 .venv/Scripts/python.exe -X utf8 scripts/train_pretrain_ko.py --tokenizer_dir tokenizers/ko_16000 --data_path data/kowiki_train_100k.jsonl 2>&1 | grep --line-buffered -v -i -E "warning|warn\(|Generating train split" | tee logs/02_pretrain_ko16000_100k.log
```

| 부분 | 이유 |
|---|---|
| `set -o pipefail` | 파이프 앞의 Python이 실패하면 전체 명령도 실패로 끝나게 한다 (없으면 마지막 `tee`의 성공 여부만 남는다) |
| `PYTHONUNBUFFERED=1` | Python 출력이 모였다가 나가지 않고 바로 나가게 한다 |
| `grep --line-buffered -v -i -E "..."` | 경고 줄과 데이터 로딩 진행 줄을 빼고, 줄 단위로 바로 넘긴다 |
| `tee` | 화면에 보이면서 동시에 파일에 저장한다 |

실시간으로 로그를 보려면 Python 쪽 버퍼링 해제와 `grep --line-buffered`가 **둘 다** 필요하다 ([02번 문서](02_사전학습_체험.md#겪은-문제) 참고).

### 로그 읽는 법

```
Epoch:[1/1](550/6250), loss: 6.8122, logits_loss: 6.8122, aux_loss: 0.0000, lr: 0.00049146, epoch_time: 51.0min
```

| 항목 | 의미 |
|---|---|
| `(550/6250)` | 현재 step / 전체 step |
| `loss` | **그 순간 배치 1개(16 조각)**의 loss. 평균이 아니라서 줄마다 오르내림이 크다 |
| `aux_loss` | MoE 모델에서만 쓰는 보조 loss. 이번 모델은 MoE가 아니라 항상 0 |
| `lr` | 현재 learning rate |
| `epoch_time` | 이름과 달리 **남은 예상 시간**이다 (원본 코드: 지금까지 걸린 시간 ÷ 진행 step × 남은 step) |

- 6,250 step 끝까지 오류 없이 완료. 로그 마지막 줄: `완료: D:\minimind_ko\out_ko/pretrain_ko16000_768.pth`
  - 경로에 `\`와 `/`가 섞인 것은 표시 문제다. 로그 02·03은 경로 표시를 정리하기 전의 스크립트로 생성됐다(동작은 같음).
- 소요 시간: **약 52분**. 로그에는 시각이 찍히지 않아서, 로그 파일이 만들어진 시각(13:45:56)과 마지막으로 기록된 시각(14:37:57)의 차이로 계산했다. 데이터 로딩 시간과 GPU 전력 제한으로 느려진 구간(아래 "겪은 문제")이 포함돼 있다.
- VRAM: 약 6.8GB (학습 중 nvidia-smi로 본 GPU 전체 사용량 약 6,770MB, 로그에는 없음. [05번 문서](05_vocab_비교.md#실험-조건))
- 결과 가중치: `out_ko/pretrain_ko16000_768.pth` (약 167MB, fp16)
- 전체 로그: [logs/02_pretrain_ko16000_100k.log](../logs/02_pretrain_ko16000_100k.log)

### loss 변화

로그의 loss는 배치 1개의 값이라 출렁임이 크다(예: 1,500 step에서 4.80이 찍혔다가 2,000 step에서 5.60). 그래서 특정 지점의 값과, 500 step 구간마다 로그에 찍힌 값 10개의 평균을 함께 적었다.

| step | 그 지점의 loss | 구간 평균 (해당 step까지 500 step) |
|---|---|---|
| 50 | 8.50 | |
| 500 | 7.04 | 7.75 |
| 1000 | 6.13 | 6.40 |
| 1500 | 4.80 | 5.94 |
| 2000 | 5.60 | 5.63 |
| 3000 | 5.28 | 5.22 |
| 4000 | 4.81 | 4.69 |
| 5000 | 4.83 | 4.50 |
| 6000 | 4.07 | 4.41 |
| 6250 (마지막) | **4.45** | 4.32 (6,001~6,250 step, 값 5개) |

- 무작위로 찍을 때의 loss는 ln(16000) ≈ 9.68이다. 첫 기록값 8.50에서 마지막 구간 평균 약 4.3까지 내려갔다.
- 감소 폭은 처음 1,000 step 동안 가장 크고, 3,500 step 이후로는 천천히 내려간다. 학습률도 계속 줄어든다(3,000 step 2.9e-4 → 6,250 step 5e-5).
- 이 loss는 vocab 16,000 기준 토큰당 값이라 [02번 문서](02_사전학습_체험.md)(vocab 6,400, 중국어)나 vocab 6,400 한국어 모델의 loss와 숫자를 그대로 비교할 수 없다. 토큰 하나에 담긴 글자 수가 다르기 때문이다. 비교는 글자당 비트(BPC)로 [05번 문서](05_vocab_비교.md)에서 한다.
- 6,400과 함께 그린 loss 그래프: [images/loss_pretrain_ko_compare.png](../images/loss_pretrain_ko_compare.png) ([05번 문서](05_vocab_비교.md#학습-loss-추이))

## 7. 생성 예시와 6,400 비교

사전학습만 한 모델로 문장 이어 쓰기를 해 본 결과와, vocab 6,400으로 같은 조건에서 학습한 모델과의 비교(검증 세트 BPC)는 [05번 문서](05_vocab_비교.md)에 정리한다.

참고: [scripts/test_pretrain.py](../scripts/test_pretrain.py)는 원본 토크나이저(`minimind/model`)와 vocab 6,400 설정이 고정돼 있어서 이번 한국어 모델에는 쓸 수 없다.

## 겪은 문제

| 문제 | 원인 | 해결 |
|---|---|---|
| 학습 도중(약 1,700~2,200 step 구간) 속도가 크게 느려짐 | GPU 전력 상한(Current Power Limit)이 21W로 묶여 있었다 (기본 35W, 최대 65W). 소비 전력 약 21W, SM 클럭 510~630MHz, throttle reason `0x4`(SW Power Cap). 온도는 54~56°C라 과열은 아니었다. 충전기 연결(PowerOnline True), Windows 전원 모드 "최고 성능"으로도 해결되지 않았다. 이 노트북은 제조사 자체 성능 모드(제조사 제어 프로그램)가 GPU 전력을 따로 정한다. | 제조사 제어 프로그램에서 성능 모드로 바꿈 → 소비 전력 약 55~59W, SM 클럭 약 2,200~2,280MHz, 온도 약 70°C로 회복 |

확인에 쓴 명령:

```bash
nvidia-smi --query-gpu=power.draw,clocks.sm,temperature.gpu,clocks_throttle_reasons.active --format=csv
nvidia-smi -q -d POWER
```

이 때문에 vocab 16,000 학습 시간은 전반부(저전력)와 후반부(고성능)가 섞여 있다. **vocab 6,400 학습 시간과 직접 비교하면 안 된다.**

## 배운 점

- 원본 코드를 고치지 않고도, 모듈 전역값을 채워 넣는 방식으로 학습 루프를 그대로 재사용할 수 있었다. 대신 원본이 어떤 전역값을 참조하는지 코드를 직접 읽어서 확인해야 했다.
- `max_seq_len`은 "대충 넉넉하게"가 아니라 실제 데이터의 토큰 길이 분포를 재서 정하는 게 좋다. 같은 글자 수라도 토크나이저에 따라 토큰 수가 달라지기 때문이다.
- 비교 실험을 할 때는 비교하려는 것(토크나이저) 외의 조건(데이터, 길이, 설정)을 똑같이 맞춰야 한다.
